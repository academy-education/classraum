# `study_item_bank.content_hash` — what actually computes it

Investigated 2026-08-06. Read-only: no row was written, no script was run
against the DB except `SELECT`s. Probe scripts lived in a scratchpad, not
in this repo.

**Answer, up front: the column is NOT reliably reproducible.** 2,681 of the
4,838 live rows (55%) cannot be regenerated by any definition — not by the
two in this repo, not by any of ~22,000 mechanically generated variants.
The 2,157 that can be regenerated need **five different definitions**, and
which one applies is a property of the cohort, not of the table.

Do not build harvest dedup on this column. A working replacement already
exists and is already applied — see [Recommendation](#recommendation).

---

## 1. Every writer

### 1a. Nothing in SQL writes it

`content_hash` is declared in `database/migrations/038_study_item_bank.sql:49`
as a plain `text` column. No `DEFAULT`, no generated expression, no trigger.
Grepped every migration for a trigger on `study_item_bank`: there are none at
all. The comment on the column (038:33-48) documents the *intended* definition
— "md5 of the item's normalized CONTENT — passage + prompt + choices … computed
by the inserter" — which is definition **A** below. It is honoured by a
minority of rows.

`038:76-78` creates a **partial unique index** on the column. This is the whole
reason the column matters, and section 5 explains why the index does not
actually protect a re-harvest.

### 1b. Live writers in the codebase (5 definitions)

`norm(s) = s.toLowerCase().replace(/[^a-z0-9]+/g, ' ').trim()` throughout.

| # | Where | Definition |
|---|---|---|
| **A** | `scripts/study-bank/bank-helper.mjs:37-39` (SAT R&W insert) and `src/lib/study/math-templates.ts:67-68` (math templates; `passage` defaults to `''`, giving the same string) | `md5([norm(passage), norm(prompt), choices.map(norm).join('\|')].join('~~'))` |
| **B** | `scripts/study-bank/math-bank-helper.mjs:34-36` (SAT math insert) and `scripts/study-bank/apply-math-hub-repair.mjs:66-68` (**overwrites** the hash on repair) | `md5([norm(prompt), choices.map(norm).join('\|')].join('~~'))` — no passage |
| **C** | `scripts/study-bank/toefl-bank-helper.mjs:59-61` (`hashListening`) | `md5([norm(passage), stripStem(prompt), choices.map(norm).sort().join('\|')].join('~~'))` — stem-stripped, **choices sorted** |

different table. Out of scope.

### 1c. The writer that produced 36% of the bank does not exist

1,761 rows carry `cohort = 'harvest-v1'` and
`verify_meta.harvested_from = 'test-cache'`. Nothing in this repo has ever
contained the string `harvested_from`, `test-cache`, or `harvest-v1` as a
writer — `git log --all -S` finds only readers (`api/admin/bank-qc/live/route.ts:369`)
and the migration that had to clean up after it (062). There is no
`study_test_cache` table in `database/migrations/` either.

**The harvest pipeline was run ad hoc and never committed.** Its hash
definition is not recoverable from this repository, and section 3 shows it is
not recoverable from the data either.

### 1d. Nine writers mutate `item` and leave the hash stale

This is the mechanism behind most of the unexplained rows. Each of these

## 3. Why they miss — two distinct causes

### Cause 1: post-insert mutation (≈920 rows)

`v3-claude`, `cr-v1`, `talk-c1`, `orphan-v1`, and 340 of `sat R&W v2` were
inserted by writers that **are** in this repo, with definitions we have.
They miss because a later repair rewrote the content.

The cleanest demonstration is within the TOEFL listening cohorts, all written
by `toefl-bank-helper.mjs` with definition **C**:

| Cohort | Created | C match | Repairs since |
|---|---|---|---|
| `cr-v2` | 07-30 | **14/14 (100%)** | none |
| `talk-c2` | 07-27 | **17/18 (94%)** | ~none |
| `talk-c1` | 07-27 | 0/24 | distractor repair |
| `cr-v1` | 07-27 | 0/56 | reshuffle + choose-a-response distractor repair |
| `v3-claude` | 07-21 | 2/325 | option-length, phrase, dash, classify |

Same writer, same definition, same week. The only variable is how many repair
passes have run over the rows since. `cr-v1` is decisive: definition **C**
sorts the choices, so `reshuffle-bank-choices.ts` alone cannot break it — the
choice **text** must have changed, which is exactly what the choose-a-response
distractor repair did.

The SAT R&W v2 split has the same signature. Hits and misses interleave within
the same insert hour (07-08T09: 157 hit / 113 miss), so it is not two writers
or two eras. It splits by **domain**:

| Domain | hit | miss |
|---|---|---|
| Standard English Conventions | 207 | 27 (**88% hit**) |
| Information and Ideas | 101 | 139 |
| Craft and Structure | 89 | 122 |
| Expression of Ideas | 14 | 52 (**21% hit**) |

Conventions options are short punctuation variants that a length/prose repair
has no reason to touch; the prose domains are precisely what `bank-repair-io.ts`
and `repair-option-length.ts` rewrote. Rows whose choices contain an em dash
are 18/20 misses, the same signal.

These rows are **unrecoverable in principle**: the hashed text was overwritten
in place and, apart from the math hub's `verify_meta.legacy_choices`, no
backup was kept. `verify_meta.legacy_choices` was tested (three definitions
over the backup) and `verify_meta.legacy_passage` was tested on the 10
phrase-repaired rows — 0 matches, because those rows are *also* harvest-v1.

**Note:** `updated_at` cannot be used to identify mutated rows. There is no
trigger on `study_item_bank`, so `updated_at` only moves when a writer sets it
explicitly, and almost none do. All 751 SAT R&W v2 rows read as "never
updated" despite demonstrably having been repaired.

### Cause 2: harvest-v1 uses an unknown definition (1,761 rows)

100% miss, every section, every item type, including 890 rows with no repair
marker in `verify_meta` at all. Mutation does not explain a rate that clean.

Two brute-force sweeps were run against these rows:

- **Sweep 1** (11,090 candidates): {md5, sha1, sha256, sha256-truncated-32} ×
  {6 normalisers: alnum-collapse, whitespace-collapse, case-preserving,
  trim-only, raw, alnum-no-space} × {11 field combinations including
  correct_answer, type, passageGroupId} × {6 field joiners} × {6 choice
  joiners} × {authored order, sorted}, plus `md5`/`sha256` of the whole
  `JSON.stringify(item)`.
- **Sweep 2** (10,800 candidates): the same digest/normaliser/joiner grid over
  six reconstructions of a *pre-split* prompt — the hypothesis that the harvest
  hashed the generated payload before `split-source-from-stem` moved the
  passage out of the prompt (`tag + passage + stem`, `passage + stem`,
  `tag + "Transcript:" + passage + stem`, …).

**Zero matches on any harvest-v1 row in either sweep.** The hashes are all
well-formed 32-hex and all 1,761 are distinct, so they are md5-shaped and were
computed per item — but over an input that is not derivable from the stored
`item`. The most likely candidates (a pre-062 `passageGroupId` like
`academic-1`, or a source-row id from the vanished test cache) are gone with
the cache.

## 4. Recommendation

### Do not use `content_hash` for harvest dedup. Do not try to repair it.

Backfilling it would require picking a definition and rewriting 4,838 rows. For
55% of them the correct input no longer exists, so the "repair" would be a
freshly invented value dressed as a recovered one — and it would silently
destroy the only dedup key the harvest-v1 rows still have against *each other*.
`apply-phrase-repair.mjs` was right to leave it alone. Keep leaving it alone.
Treat it as an **opaque legacy token**, valid only for equality against another
value produced by the same vanished era.

### Use `public.study_item_content_sha(jsonb)` instead — it already exists and is already applied

Migration `076_review_content_binding.sql:56-76` defines an `immutable` SQL
function:

```sql
md5(coalesce(item->>'prompt','')         || chr(31) ||
    coalesce(item->>'passage','')        || chr(31) ||
    coalesce(item->>'correct_answer','') || chr(31) ||
    coalesce((item->'choices')::text,''))
```

Verified live during this investigation: the function is deployed,
`study_item_reviews.item_sha` is populated, and it was **reproduced exactly in
JavaScript on 20/20 rows**, so it is usable from both the SQL and the script
side of the pipeline. It is computable over *any* row at *any* time, which is
the property `content_hash` lacks.

Concretely:

1. Add `content_sha text generated always as (public.study_item_content_sha(item)) stored`,
   with a unique index on it. Generated + stored means **no writer can forget
   to update it** — the failure mode of all nine scripts in section 1d becomes
   structurally impossible.
2. Point harvest dedup at `content_sha`. Leave `content_hash` in place,
   unread by new code, as a historical artefact.
3. Before doing so, decide two things the review-oriented definition gets
   deliberately "wrong" for dedup:
   - It hashes **raw** text, so a whitespace or punctuation edit is a new item.
     That is correct for review staleness (076's purpose) and wrong for dedup.
   - It hashes choices in **stored order** (076:49 says so explicitly), so a
     `reshuffle-bank-choices.ts` run creates a false "new item". The
     14-copies-of-one-reef-question incident that `toefl-bank-helper.mjs:45-56`
     describes is exactly this failure.

   If `content_sha` is to be the dedup key, add a **second** normalised,
   order-insensitive column for that job — definition **C**'s shape
   (`norm` + `stripStem` + sorted choices) is the one in this repo that has
   already survived that specific bug. Do not overload one column with both
   jobs; that overloading is how we got here.

### Independent of any of the above: the unique index is not protecting the bank

`038:76-78` is `UNIQUE … WHERE content_hash IS NOT NULL`. Because 55% of rows
carry a hash no current definition reproduces, a re-harvest of an item already
in the bank will compute a *different* hash, miss the in-memory `seen` set,
**and pass the unique index** — inserting a duplicate. The index reads as a
guarantee and is not one. 062's closing note ("28 items with only 14 distinct
prompts — the harvest let near-duplicate questions through content_hash
dedup") is that failure already observed once.

Until a reproducible key is in place, any new harvest should dedup on
normalised content computed at harvest time over the **live bank as read**,
not on the stored column.
